# D-0002 — Hold-to-fire is a press/release message and a server clock, never `Item.use`

**Decision**: With a gun in the main hand the client cancels
`InputEvent.InteractionKeyMappingTriggered` for the use key (and the swing),
and sends one `TriggerPayload(held)` on press and one on release. The server
keeps a per-player transient attachment (`held`, `nextShotAt`, the
empty-click latch, a pending reload request) and runs the trigger's rule
table in `PlayerTickEvent.Post`. The reload key is a payload on the same path.
No `Item.use`, no `startUsingItem`, no item cooldown.

**Why**: Verified in NeoForge 21.1.248: `Minecraft.startUseItem` sets a
four-tick right-click delay before the event fires, repeats the event at most
every four ticks while the key is held, and never once the player
`isUsingItem()`; and `LocalPlayer.aiStep` multiplies movement input by 0.2
while using an item. Vanilla's path therefore caps a held trigger at five
rounds a second, and the two ways of holding it either strobe the hotbar
cooldown or slow the player. A machine gun at three ticks needs its own
clock, and the clock must be the server's so the rate is authoritative. A
message per edge, not per shot, keeps the traffic to two packets per burst.

**Alternatives rejected**: *`Item.use` plus `useOnRelease`* — the repeat cap
above. *A client-side clock sending a packet per shot* — the client would set
the rate. *Mixins into `Minecraft.startUseItem`* — the event already returns
from the whole method when cancelled; no mixin needed.

**Follow-ups**: A gun in the off hand is not a gun; the trigger is the main
hand only.
